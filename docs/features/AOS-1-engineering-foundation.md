## 1.1 Repo setup ✅ (the "passing CI" gate completes in 1.5)

**Goal:** changes reach `main` only through a reviewed PR.

**Decisions**
- The repo was made **public** (PO decision, 2026-11-01). GitHub's free plan only supports branch protection on public repos, and the project is a portfolio piece.
- **Required approvals = 0:** this is a solo-developer repo, and GitHub doesn't let authors approve their own PRs. Review is done by the `code-reviewer` agent before each commit, plus the PO at sprint demos. Required CI status checks are added in task 1.5, once the pipeline exists.

**Configuration (`main` branch protection)**

| Setting | Value | Why |
|---------|-------|-----|
| Require a pull request | ✅ (0 approvals) | No direct pushes to `main` |
| Enforce for admins | ✅ | The rule applies to the repo owner too |
| Dismiss stale reviews | ✅ | Only takes effect if approvals are required later |
| Require linear history | ✅ | Clean, readable history |
| Require conversation resolution | ✅ | Every review comment is addressed before merging |
| Allow force pushes | ❌ | History can't be rewritten |
| Allow deletion | ❌ | `main` can't be deleted |
| Required status checks | *(added in 1.5)* | CI must pass before merging |

**Repository settings:** squash merge only (one commit per PR on `main`), with branches automatically deleted after merging.

**Files**
- `.github/pull_request_template.md`: what and why, testing, screenshots, and the Definition of Done checklist

**Trust boundary until 1.5:** with admins enforced, the owner can't push directly or bypass the rules, but can merge their own PRs (0 approvals required).

**How it was verified:** read the protection back through the GitHub API on 2026-11-01; this PR itself is the first change to reach `main` through the new flow.

## 1.2 Project scaffolding ✅

**Goal:** a running Next.js + TypeScript + Tailwind + Framer Motion app with the folder structure from the [technical design](../08-tech-design.md#3-folder-structure).

**What was set up**
- Next.js **16.4.3** (App Router, `src/` directory, `@/*` import alias), React 19, TypeScript (strict), Tailwind CSS 4, Framer Motion, ESLint (Next.js core-web-vitals + TypeScript rules)
- Fonts from the UX design through `next/font`: Space Grotesk (headings), Inter (body), JetBrains Mono (commands)
- Dark space theme tokens in `src/app/globals.css` (background `#050816`, foreground, muted, accent)
- A placeholder home page with the landing tagline `npm install experience`, replaced by the map in AOS-2
- The full folder structure from the technical design, with `.gitkeep` placeholders: `src/components/{map,astronaut,station,progress,onboarding,search,knowledge-base,ui}`, `src/lib/{map,content,progress,analytics}`, `content/{stations,knowledge-base}`, `tests/{unit,e2e,visual}`, `infra/terraform`

**Decisions**
- **Kept the template's settings** (`cacheComponents` and `partialPrefetching` set explicitly in `next.config.ts`, Turbopack as the bundler). Static pages still pre-render fully (`○` in the build output), which is what ADR-2 needs.
- **Tailwind runs through the `@tailwindcss/turbopack` loader** configured in `next.config.ts` (from the Next.js 16.4 template). This is deliberate: don't add a second `postcss.config.mjs` setup.
- **Node 24** is pinned via `.nvmrc` and `engines`, with matching `@types/node`; TypeScript also has `noUncheckedIndexedAccess` on, so array and record lookups are type-safe.
- **`AGENTS.md`** (generated by Next.js) is committed and referenced from `CLAUDE.md`. This Next.js version is newer than common training data, so its bundled docs in `node_modules/next/dist/docs/` must be read before writing Next.js code.
- **`output: 'standalone'`** is deferred to task 1.6 (Docker), where it's needed.

**Known issue: `npm audit`** reports 16 moderate findings, all from one denial-of-service advisory in `minimatch` pulled in by **ESLint (development only)**. None of it ships to users. npm's suggested "fix" downgrades ESLint to v4, which is worse, so it's accepted for now. The CI dependency scan (task 1.5) will fail on **high or critical findings in production dependencies**.

**How it was verified:** `npm run lint` passes; `npm run build` pre-renders `/` as static; `next start` serves the page with the title "The Art of SDLC".

**Decisions**
- **Auto-fix instead of reject (AC refined):** the hook rejects *unfixable* lint errors and auto-fixes formatting; CI's `format:check` rejects anything unformatted that bypassed the hook. A test commit with `export const bad: any = 1` was rejected.
- **`prepare: husky || true`:** installs without devDependencies (the Docker production stage in 1.6) don't fail.
- **Markdown excluded from Prettier;** the type check runs in CI, not the hook (too slow per commit).
- **Firefox is verified in CI only.** Playwright's Firefox fails to launch on the dev Mac ("Could not find profile folder") but passes on the Linux CI runner; locally `npm run test:e2e:local` runs Chromium and WebKit.
- **Visual baselines are per platform:** macOS locally, Linux in CI. New Linux baselines come from the CI `visual-results` artifact and are committed after review.
- **Zoom-level screenshots** (spike lesson L4) are added with the map in AOS-2.3; this story sets up the infrastructure with a home-page screenshot.

### Canary runbook

1. Push the release to `main`? **No.** Deploy the candidate as a preview, e.g. from a `release` branch, and copy its deployment URL.
2. In Vercel production env vars, set `CANARY_URL` (the candidate URL) and `CANARY_PERCENT` (25 at launch, given low traffic), then **Redeploy** production.
3. Put yourself on the canary: set the cookie `aos-canary-bucket=0` in the browser.
4. Watch the dashboard's "Canary vs stable" table. Promote only once NEW has real page views and no worse errors or LCP.
5. **Healthy:** raise the percentage (50), then promote: merge to `main`, and remove the canary vars. **Unhealthy:** set `CANARY_PERCENT=0` and redeploy, which puts everyone back on stable.

### 1.7 review fixes

Review of the canary router found these; all fixed, the router changes each with a unit test:

- **Bypass secret could leak:** the canary target was built from the request path, so `//evil.example` could pick the host. The target now takes only the path and query; the origin always comes from `CANARY_URL`.
- **`CANARY_URL` limited to our own deployments:** only `https://*.vercel.app` (or `localhost` for tests); anything else turns the canary off.
- **Loop guard:** no routing if `CANARY_URL` is this same site.
- **First request is always stable** (it sets the bucket cookie), so crawlers and cookie-less clients never reach the canary.
- **Matcher:** static files skip the proxy, except `/_next/static` for visitors with a bucket (canary pages need the canary's files).
- **Release tag from the first event:** `release` moved from the loader's `onLoad` into `NREUM.info.jsAttributes`.
- CSP allows the Vercel toolbar on **preview** deployments only (UAT comments); the obsolete `interest-cohort` is gone from Permissions-Policy; "Sessions" removed from the canary-vs-stable widget.
